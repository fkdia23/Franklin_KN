> [!NOTE]
> I did not take part in this competition. This post breaks down the winning
> solution published by the Numina team, based on their own sources (links at
> the end), and what I take away from it for my own projects.

**In short:** a **7-billion-parameter** model, fine-tuned in two stages to
**reason by writing and running Python**, then queried **48 times in
parallel** with a majority vote. Result: **29 problems solved out of 50** on the
private leaderboard, with two T4 GPUs and 9 hours of compute.

## 1. The competition at a glance

| Item | Detail |
| --- | --- |
| **Competition** | AI Mathematical Olympiad — Progress Prize 1 (Kaggle) |
| **Dates** | April 1 → June 27, 2024 |
| **Participation** | 1,161 teams, 1,831 submissions, 81 countries |
| **Task** | 50 math problems per leaderboard (public / private), AMC12 to AIME level, **integer** answers |
| **Constraints** | 1 P100 GPU **or** 2 T4 GPUs, **9 h** max per submission, 2 submissions per day |
| **Allowed models** | open-weight, released before February 23, 2024 |
| **Winner** | team **Numina** (with Hugging Face) — **29/50**, $131,072 |

The difficulty is not only mathematical: you have to get through **50 problems
in 9 hours on modest hardware**. Every choice (model size, number of samples,
quantization) is paid for in compute time.

Two philosophies: Numina bets everything on **one very well-trained model**
and the law of large numbers; CMU adds **a judge** (the reward model) to break
ties between candidates.

## 3. Stage 1 — learning to reason (Chain of Thought)

The first fine-tuning stage teaches the model to **write a step-by-step
solution**. The dataset ranges from high-school exercises to olympiad problems,
and building it is real data engineering work:

1. **OCR** of the original PDFs;
2. **segmentation** into problem / solution pairs;
3. **translation** into English;
4. **realignment** of the solutions into a _Chain of Thought_ format;
5. **normalization** of the final answer.

| Hyperparameter | Stage 1 (CoT) | Stage 2 (TIR) |
| --- | --- | --- |
| Learning rate | 2.0e-5 | 2.0e-5 |
| Total batch size | 32 | 32 |
| Sequence length | 2,048 | 1,024 |
| Epochs | 3 | 4 |
| Scheduler | cosine, warmup 0.0 | cosine, warmup 0.1 |

On the infrastructure side: **full fine-tuning** (no LoRA), gradient
checkpointing, DeepSpeed ZeRO-3 and TRL's `SFTTrainer` with packing. According
to the project repository, training takes **about ten hours on one node of
8 × H100**.

## 4. Stage 2 — learning to use Python (Tool-Integrated Reasoning)

The second stage changes everything: the model is no longer just a writer, it
**delegates computation to Python**. Each solution interleaves reasoning, code
and execution output (ToRA format). To build it, the team selected **~60,000
problems with numerical answers**, had GPT-4 generate solutions **three
times**, and kept only those that reached the correct answer.

Here is what the format looks like, on a simplified example of my own:

````text
Problem: how many integers between 1 and 1000 are divisible by 3 or by 5?

Count the multiples of 3 and of 5, then remove the multiples of 15, which were
counted twice (inclusion-exclusion). Let's check by computing it:

```python
print(sum(1 for n in range(1, 1001) if n % 3 == 0 or n % 5 == 0))
```
```output
467
```
The answer is 467.
````

> [!IMPORTANT]
> The key idea: an LLM often gets **arithmetic** wrong, but rarely gets the
> **code that does the arithmetic** wrong. Handing computation to Python
> removes a whole class of errors.

The gain is clear on the MATH benchmark: **56.3%** for the CoT-only model,
**about 68%** for the TIR model.

## 5. Inference: SC-TIR, the real secret weapon

At inference time, Numina combines **self-consistency** and **code execution**
under the name **SC-TIR**:

1. copy the problem **N = 48** times to build a batch of prompts;
2. sample each candidate until the end of a Python code block;
3. **execute** each block and feed the output back — tracebacks included,
   which lets the model **correct itself**;
4. repeat **M = 4** times;
5. **prune** invalid candidates (incomplete code, no answer);
6. **majority vote** over the remaining answers.

As pseudo-code (simplified, helper functions are implied):

```python
from collections import Counter

def sc_tir(problem, llm, run_python, n=48, m=4):
    drafts = [make_prompt(problem)] * n          # N copies of the problem
    for _ in range(m):                            # M generate + execute rounds
        drafts = llm.generate(drafts, stop=["```output"])
        for i, text in enumerate(drafts):
            code = last_python_block(text)
            if code and not has_final_answer(text):
                output = run_python(code)         # output or traceback
                drafts[i] = f"{text}```output\n{output}\n```\n"
    answers = [extract_answer(d) for d in drafts]
    answers = [a for a in answers if a is not None]   # pruning
    return Counter(answers).most_common(1)[0][0]      # majority vote
```

To fit the budget, the model is **quantized to 8 bits** with AutoGPTQ
(calibrated on the training data) and served with **vLLM**: T4 GPUs do not
support bfloat16 and their memory is limited.

## 6. Validating without overfitting the public leaderboard

With only 50 public problems, the leaderboard is very noisy. The team relied
on **four internal validation sets** instead:

| Set | Size | Purpose |
| --- | --- | --- |
| AMC (AMC12 2022-2023) | 83 problems | close to the hidden test; ~60-65% solved |
| AIME (2022-2024) | 90 problems | hard problems, failure modes |
| MATH level 4 | 754 problems | volume, integer answers |
| MATH level 5 | 721 problems | volume, hardest problems |

Even with SC-TIR, the score varies by **1 to 3%** from one random seed to
another: without these sets, there is no way to tell whether an "improvement"
is real.

## 7. What did not work (and why it matters)

- **CoT only + majority vote**: capped at 8/50 on the public leaderboard.
- **MMOS** (a single Python program per solution): capped at 16/50 — one round
  of code is not enough for hard problems.
- **Bigger models** (InternLM-20B, CodeLlama-33B, Mixtral-8x7B): too slow on
  2 × T4, and DeepSeekMath 7B remained hard to beat.
- **RL** (PPO, RLOO): no significant gain.
- **KTO**: slightly better (27/50 on the public leaderboard), but there was no
  time left to apply it to the final model.
- **Model merging** (DARE, TIES, WARP): regressions.
- **Static KV cache and `torch.compile`**: errors on Kaggle's T4s.

## 8. What I take away for my own projects

- **Data before model size.** Under a compute budget, a well-trained 7B beat
  much larger models (20B, 33B, Mixtral 8x7B) that were too slow for the
  budget.
- **Let the tool do the math.** That is the principle behind my
  [SQL agent](/posts/agent-sql-equipes-metier/) (in French): the LLM writes the query, the
  database computes. Here, the LLM writes the Python, the interpreter computes.
- **The inference budget is a hyperparameter.** N × M sets the trade-off
  between accuracy and time: measure it, don't guess it.
- **Validate internally, not on the public leaderboard.** Use sets that mimic
  the hidden test, and several seeds.
- **Full fine-tuning or LoRA?** Numina could afford full fine-tuning on
  8 × H100. With less compute, LoRA / QLoRA with Unsloth, as in my
  [Qwen2.5-Coder project](/posts/llm-finetuning-domaines-metiers/) (in French),
  remains the pragmatic path.
